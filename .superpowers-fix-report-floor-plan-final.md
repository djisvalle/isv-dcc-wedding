# Floor Plan Canvas — Final Whole-Branch Review Fix Report

Date: 2026-08-10
Scope: `src/pages/admin/AdminTables.tsx`, `src/components/admin/tables/TableFloorPlan.tsx`
Context: This work was already merged onto `main` before this review; there is no separate
feature branch or `.superpowers/sdd` workspace for it (the prior one was lost to a worktree
cleanup). All fixes below were made directly on `main` as new commits, per instructions.

## Fix 1 (Critical) — first-time-placement race against the async settings load

### Problem
`AdminTables` builds `activeTables` from two sources: a synchronous guests-derivation effect,
and an async `getDoc(doc(db, 'settings', TABLE_LAYOUT_SETTING_ID))` — the only source of empty
tables, custom per-table capacities, and saved floor-plan positions. If the Floor Plan tab
mounted before that `getDoc` resolved, `TableFloorPlan`'s auto-placement effect would see every
table as "missing a layout" and call `onAssignDefaultLayouts`, which does a `setDoc` that
**replaces** the whole settings document — silently dropping anything that only lived in the
not-yet-loaded document. The in-flight `getDoc` then resolved and locally patched the view via
`mergeTables`, so nothing looked wrong until the next reload.

### Fix
Added a `layoutLoaded` state flag in `AdminTables`, set to `true` on every terminal branch of the
settings-load effect:
- success path (after `setActiveTables(prev => mergeTables(saved, prev))`)
- `!snap.exists()` (first-ever use / no saved settings yet)
- `raw` not a string
- `saved` not an array
- the `JSON.parse` `catch` block (malformed data)
- the outer `.catch(err => ...)` — **set before** calling `handleFirestoreError`, since that
  helper always re-throws (confirmed by reading `src/lib/firebase.ts:36-55` — it logs then
  `throw new Error(...)`), so anything scheduled after the call would never run. This was a
  necessary correction beyond the reviewer's exact wording, otherwise the error path would have
  reproduced the very bug being fixed (an unhandled Firestore GET error would leave
  `layoutLoaded` stuck at `false` forever).

The `TableFloorPlan` mount (and thus its auto-placement effect) is now gated:
```tsx
) : !layoutLoaded ? (
  <div className="bg-white rounded-3xl border-2 border-dashed border-slate-100 py-20 text-center text-slate-400">
    <p className="font-serif text-lg text-slate-600 mb-1">Loading floor plan…</p>
    <p className="text-sm">Just a moment while we load your saved layout.</p>
  </div>
) : (
  <TableFloorPlan ... />
)
```
This closes the race by construction — the canvas cannot mount before the settings doc read has
definitively settled, one way or another.

## Fix 2 (Important) — mobile notice was CSS-only, canvas still mounted (and wrote) on phones

### Problem
The mobile notice and the canvas wrapper were both always rendered, toggled only via Tailwind
`md:hidden` / `hidden md:block`. `TableFloorPlan` still mounted inside a `display:none` container
on phones — its auto-placement effect still ran and still wrote to Firestore, and React Flow
initialized against a zero-size parent.

### Fix
Added a small `useMediaQuery` hook (no existing one in the codebase) directly in
`AdminTables.tsx`, seeded from `window.matchMedia('(min-width: 768px)').matches` and kept in
sync via a `change` listener:
```tsx
function useMediaQuery(query: string): boolean {
  const [matches, setMatches] = useState(() =>
    typeof window !== 'undefined' ? window.matchMedia(query).matches : false
  );
  useEffect(() => {
    const mql = window.matchMedia(query);
    const handleChange = () => setMatches(mql.matches);
    handleChange();
    mql.addEventListener('change', handleChange);
    return () => mql.removeEventListener('change', handleChange);
  }, [query]);
  return matches;
}
```
`isDesktopViewport = useMediaQuery('(min-width: 768px)')` now drives a real conditional mount
(the notice OR `TableFloorPlan`, never both) instead of a CSS toggle. This combined naturally
with Fix 1 into a single three-way conditional (mobile notice / loading notice / canvas) in the
`view === 'floorplan'` render branch.

## Fix 3 (Important) — multi-select left enabled despite being a stated non-goal

### Problem
React Flow's defaults leave shift-box-select and ctrl/cmd-click multi-select active. Dragging a
multi-selected group visually moves every selected node, but the drag-stop handler only persists
the one explicitly-grabbed node, so the others silently snap back on the next state sync.

### Fix
In `TableFloorPlan.tsx`, added to the `<ReactFlow>` element:
```tsx
selectionKeyCode={null}
multiSelectionKeyCode={null}
```
This disables shift-box-select and ctrl/cmd multi-select entirely, while leaving single-node
click-to-select (which the rotate/shape UI depends on) untouched.

## Fix 4 (Important) — Print button broken while on the Floor Plan tab

### Problem
The Print button lives in the shared page header, outside the `view === 'list'` branch, but the
entire printable seating grid only exists inside that branch. Clicking Print from the Floor Plan
tab produced a page with just the header and an unprintable canvas.

### Fix
```tsx
{view === 'list' && (
  <Button onClick={handlePrint} variant="outline" className="border-slate-200 rounded-2xl h-12 print:hidden">
    <Printer className="w-4 h-4 mr-2" />
    Print Seating Chart
  </Button>
)}
```
Restores pre-existing behavior (Print was never broken before the floor-plan feature) rather than
attempting to make printing work from the canvas view, which is out of scope.

### Behavioral verification (Playwright harness, temporary, deleted before commit)
No live admin credentials were available for `/admin/tables` (real Firebase auth + Firestore
project required). Per the suggested approach, I built a temporary Playwright harness:

- `src/pages/admin/__FloorPlanFixHarness.tsx` (temporary, deleted): a small component that
  duplicates the exact `useMediaQuery` hook and the `layoutLoaded` gating state machine used in
  `AdminTables.tsx`, wraps the **real** `TableFloorPlan` component (which has no Firebase
  dependency of its own — it only takes props/callbacks) with two mock tables, one of which has
  no `layout` (to trigger the auto-placement effect if the canvas mounts early), and a simulated
  1.5s async delay standing in for the real `getDoc` call.
- A temporary route `/__harness/floorplan` was added to `src/App.tsx` to serve it via the Vite
  dev server.
- A Playwright script drove three scenarios against `localhost:5183`:
  1. **Desktop, before the simulated settings load resolves**: `layoutLoaded=false`,
     `mounted=false`, loading notice shown, `.react-flow` never rendered, `assignCalls=0`.
     **Confirms Fix 1**: the canvas cannot mount (and cannot fire the destructive
     auto-placement write) before the settings load settles.
  2. **Desktop, after the simulated load resolves**: canvas mounts (`.react-flow` count 1),
     auto-placement effect fires for the layout-less mock table (`assignCalls` became 2, not 1 —
     traced to `React.StrictMode` in `src/main.tsx`, which double-invokes effects in development
     only; this is expected React dev behavior, not a bug in the fix, and does not occur in
     production builds).
  3. **Mobile viewport (375×700) throughout, including past the simulated settings-load delay**:
     mobile notice shown, `.react-flow` never rendered, `assignCalls=0` even after the delay
     elapses. **Confirms Fix 2**: the canvas never mounts below the breakpoint, regardless of
     load timing — not just visually hidden.
  4. **Resize from desktop to mobile after the canvas is already mounted**: `.react-flow` count
     drops from 1 to 0 and the mobile notice appears. **Confirms Fix 2's live `matchMedia`
     listener** correctly unmounts the canvas on a breakpoint crossing, not just on initial load.

One implementation snag worth noting: my first harness pass passed inline (non-memoized) arrow
functions as `onAssignDefaultLayouts`/`onUpdateLayout`, which gave `TableFloorPlan`'s
auto-placement effect a new function identity on every render and caused an artificial infinite
loop (`assignCalls` hit 648). This was a bug in the *harness*, not the production code — the real
`handleAssignDefaultLayouts`/`handleUpdateLayout` in `AdminTables.tsx` are both wrapped in
`useCallback` with an empty dependency array, so they're stable across renders. I fixed the
harness to match (also via `useCallback`) and reran; the count dropped to the expected small,
finite number (2, per the StrictMode note above).

After verification, the harness file and the temporary route in `App.tsx` were deleted. Confirmed
via `git status --short` that only the two intended files
(`src/components/admin/tables/TableFloorPlan.tsx`, `src/pages/admin/AdminTables.tsx`) show as
modified, and `git diff -- src/App.tsx` is empty — the harness never entered the index.

## Concerns
- The "Loading floor plan…" placeholder shown during the `!layoutLoaded` window is new UI that
  didn't exist before (previously the canvas would just render immediately, correctly or not).
  It should only be visible briefly (one Firestore round-trip) in normal use — worth a quick
  visual sanity check by the user when they next have access to the real admin route.
- `layoutLoaded` intentionally only reflects "the load attempt is over," not "the load succeeded
  with data." This matches the spec's stated intent (a legitimately-empty settings doc, e.g.
  first-ever use, must not block forever) but means a *persistent* Firestore GET failure (e.g.
  permissions misconfiguration) will still let the canvas mount — at that point `activeTables`
  is guests-derived only, so the auto-placement effect will assign default layouts and persist
  them, which is the intended pre-existing behavior for "no saved layout" and not a regression
  introduced by this fix (the effect's write path is unchanged; only the *timing* of when it's
  allowed to run was fixed).
